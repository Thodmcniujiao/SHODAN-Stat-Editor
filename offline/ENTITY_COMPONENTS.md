# 实体组件视图

入口为顶部“实体组件”。“生命与拆毁”子页上方切换“生命组件”“实体拆毁”“淹没组件”“护盾组件”“接触伤害”；“地雷与投掷”子页上方切换“地雷组件”“地雷生成器组件”“投掷物组件”“投掷器组件”。飞鹰参数从“轨道飞鹰 → 飞鹰编辑”访问。原“敌人设置”以及炮台、载具等原有页面继续保留。

## 已确认的 ECS 结构

游戏的 `generated_entities.dl_bin` 按组件类型分块。组件数据表通常包含“实体哈希 → 记录索引”的映射，以及组件记录数组；实体的资源目录并不需要分别存放每一个组件。`dl_library.dl_typelib` 描述记录布局，原编辑器将这些表映射为可读写字段。

| 原页面中的内容 | 数据来源 | 本次视图 |
| --- | --- | --- |
| 全身生命、护甲、耐久比例、爆炸承伤、流血生命、再生及延迟 | HealthComponentData 的 Health 记录 | 实体组件 → 生命 |
| 面部、各腿、双爪等部位的生命、护甲、耐久、爆炸承伤、伤害传递和致死标志 | 同一 Health 记录内的部位数组 | 同一实体下按部位分组 |
| 移动速度、行为状态速度 | AiEnemy / AiCharacter 等组件 | 保留在原页面 |
| 视觉、听觉、感知 | SensorEye / SensorEar 等组件 | 保留在原页面 |
| 拆毁抗性阈值 | 按 Unit / 实体映射的 DestructionSettings 与 DestructionTemplates | 实体组件 → 实体拆毁 |

当前布局中，Health 记录长 22096 字节。全身生命在记录 +0；再生 +4；再生延迟 +12；流血生命 +24；耐久比例 +268；护甲 +280；爆炸承伤 +388。部位数组从 +520 开始，最多 38 项、每项 552 字节；部位内耐久比例 +204、护甲 +216、生命 +232、致死标志 +244、传递给身体的伤害 +248、爆炸承伤 +324。这里按原编辑器已经验证的布局开放字段，并沿用其有效值检查；继承值或无有效数据的字段不会伪造为可编辑的零值。

`Health.on_death_destruction_level` 是死亡时采用的破坏类型，不是实体承受的拆毁阈值。移动和感知字段也不属于 Health，不能仅按界面上的相邻位置把它们归入生命组件。

## 生命页

两页共用完整实体目录，不局限于拥有当前组件的实体。当前离线数据合并出 3465 项，其中 506 项拥有 Health 组件、1795 项存在破坏映射。缺少本页组件或配置的名称显示为灰色，默认显示；取消“显示无本组件的实体”后可隐藏。分类框、搜索、滚动、参数编辑、恢复和预设控件在两页保持相同，切换保留当前实体、搜索词及分类。

支持通过 `entity_catalog.json` 自定义分类、分类规则和实体名称，点击“重载JSON”生效；“打开分类JSON”可打开实际文件。完整格式、路径和外部索引参见 `ENTITY_CATALOG_API.md`。阿尔法指挥官等已知敌人的面部、腿、爪名称保持可读。

生命页与原页面使用同一个字段对象。原页面已经拥有的字段继续保存到原来的配置条目；新页面没有单独的生命值配置副本。两边的编辑、恢复、预设以及修改开关因此作用于同一份数据。原页面把多个变体一起编辑时仍保留原行为；生命页则按实际实体映射查看对应记录。

若多个实体指向同一条 Health 记录，标题下会提示共用数量，修改会一起生效。本次是组件视图和编辑入口的汇总，不会自动克隆 Health 记录。拆毁页已有的私有模板与 Unit 隔离方案不改变这一点。

## 淹没页

“实体组件 → 生命与拆毁 → 淹没组件”列出完整实体目录中每个实体的 DrownableComponentData（类型哈希 0x726A4F6B，记录 64 字节）。字段按组件自身的顺序排列：

| 偏移 | 字段 | 类型 |
| --- | --- | --- |
| +0 | drown_enter_node | 节点名哈希（u32） |
| +4 | drown_enter_offset（原名：溺水深度偏移） | f32，可为负 |
| +8 | drown_float_surface_offset（原名：漂浮深度偏移） | f32，可为负 |
| +12 | drown_time（原名：溺水前时间） | f32 |
| +16 | drown_recovery_multiplier | f32 |
| +20 | drown_callout_delay | f32 |
| +24 / +25 / +26 | slow_while_submerged / slow_while_drowning / should_die | 布尔（1 字节） |
| +28 | slow_strength | f32 |
| +32 | buoyancy_loss | f32 |
| +36 / +40 | slow_depth_start / slow_depth_max | f32 |
| +44 | slow_base_nodes[4] | 4 个节点名哈希（u32） |
| +60 | should_float | 布尔（1 字节） |

+4、+8、+12 是原编辑器已验证的字段。其余字段在启动时与游戏类型库（dl_library.dl_typelib）中该组件记录的字段偏移和大小逐一核对，完全一致才开放；不一致或类型库不可用时只显示这三项，原因写入日志（以 `drownable:` 开头）。

排版、分类框、搜索、“显示无本组件的实体”、恢复和预设与生命页相同，三页之间切换保留当前实体。绝地潜兵的这三个字段与原页面（额外 → 绝地潜兵）是同一个字段对象，继续保存到原来的配置条目，两边同步；多个实体共用同一条记录时，标题下提示共用数量。实现见 `offline/drown_components.lua`。

“实体组件 → 生命与拆毁 → 护盾组件”列出完整实体目录中每个实体的 ShieldComponentData（记录 344 字节）。页面最上层是“护盾组件（Shield）”，其下按参数组排列，共 83 项：

| 参数组 | 字段（偏移） |
| --- | --- |
| 容量与充能 | charge +0x4C、recharge_delay +0x58、broken_recharge_delay +0x5C、recharge_rate +0x60、starter_charge_on_recharge +0x64、start_offline +0xB0、未知浮点数 +0x50 / +0x68 |
| 形状与外观 | radius +0x00、shield_shape +0x144（枚举）、shield_node +0x04、visual_sphere_path +0x78（u64）、inside_shield_opacity +0xE4、shield_color_type +0xE8（枚举）、未知浮点数 +0x70 |
| 行为 | block_melee_type +0xE0（枚举）、hit_effect_receiver_type +0xD8（枚举）、inflict_pain +0xDC、linked_to_status_effect_volume +0xEC、状态效果类型 +0x6C（StatusEffectType）、未知开关 +0x54 / +0xAC / +0xAD / +0xAE / +0x150 |
| 充能事件 1–4 | charge_event_triggers[4]，从 +0xF0 起每项 20 字节：health_percent、event_name、reverse_event_name、event_sound、reverse_event_sound |
| 音效 | +0x88 至 +0xC8 的各音效事件哈希，及 charge_event_trigger_audio_node +0x140 |
| 动画与特效 | shield_break_particles +0x80（u64）、充能循环事件节点 +0xC4、单位上线节点 +0xCC、激活 / 关闭动画事件 +0xD0 / +0xD4 |
| 未知字段 | +0x08、+0x0C 起 16 个 u32、+0x148（u64） |

字段名和偏移来自游戏 1.007.200 的类型库转储（[Darctor/Helldivers2_RawData](https://github.com/Darctor/Helldivers2_RawData)，ShieldComponentData.json），并经过双重验证（见下文“验证”）。

枚举字段在名称后显示当前取值的名称：颜色（无 / 光能者蓝 / 绝地潜兵橙）、近战阻挡方式（无 / 伤害一次后关闭区域形状 / 伤害一次后关闭伤害结果）、状态效果类型（按状态效果表取名）；形状类型和命中特效接收类型暂无取值名称，只显示数值。u64 资源哈希按完整十进制输入和显示。

排版、分类框、搜索、“显示无本组件的实体”、恢复和预设与生命页相同。SH-32、SH-51、FX-12、G/SH-39 原页面已有的护盾字段与本页是同一个字段对象，继续保存到原来的配置条目，两边同步；多个实体共用同一条记录时，标题下提示共用数量。实现见 `offline/shield_components.lua`。

## 投掷物页

“实体组件 → 投掷物”和“实体组件 → 投掷器”是两个子页，对应两个不同的组件：

- **投掷物（Throwable）**：被扔出去的东西本身，即手雷、飞刀、地雷模型等。
- **投掷器（Thrower）**：负责把投掷物扔出去的东西，即地雷投放舱和 G-11 铁蒺藜的旋转发射体。它的 `throwable_path` 指向它扔出的投掷物实体。

投掷物组件里名字带 `thrown` 的字段（`on_thrown_audio_event`、`thrown_trail_effect`、`destroy_thrown_trail_effect_on_attach`）是投掷物自身“被扔出后”的音效和尾迹，仍属于投掷物组件。

**投掷物组件（ThrowableComponentData，360 字节，78 项）** 就是手雷等页面里“投掷物”一段的来源：最大投掷距离 +16，初始数量 +100、最大携带 +104、来自补给 +108。参数组：

| 参数组 | 内容 |
| --- | --- |
| 投掷 | 最小 / 最大投掷距离、投掷者速度叠加 / 扣除 / 死区、角速度开关、最小 / 最大角速度（XYZ） |
| 携带数量 | 初始数量、最大携带、来自补给、同时存在上限（i32，-1 为不限） |
| 粘附与触发 | 粘附、粘附延迟、撞击触发、忽略与投掷者的撞击、取消时掉落、可交互延迟 |
| 引信 | fuse_settings[6]：每项时间、未知 64 位值、能力 ID |
| 实体与动画 | 物理体、延迟物理体及时长、投出语音、各动画事件、能力 ID |
| 音效与尾迹特效 | 投出 / 弹开音效、尾迹特效（UnitEffect：粒子、位置与旋转偏移、节点、发射事件、脱离宿主时，以及 +44 字节的 5 个标志位：继承旋转、跟随宿主、在相机处生成、未知位 3 / 4）、粘附时移除尾迹 |
| 未知字段 | +0x44、+0xB0 / +0xB4、+0x148 / +0x14C / +0x150、+0x154（开关）、+0x158、+0x15C、+0x160、+0x164 |

**投掷器组件（ThrowerComponentData，752 字节，186 项）** 是地雷投放舱和 G-11 铁蒺藜：2 个编队，每个 376 字节。每个编队包括面板数、每面板投掷物数、抛射延迟 / 持续时间、解除保险时间、转速、停转时间、抛射速度范围、俯仰 / 偏航 / 滚转偏移、散布，投掷物实体哈希和各音效，抛射特效（UnitEffect），48 个抛射节点，以及未知字段。面板数和每面板投掷物数只能调低：超过游戏原值会使游戏崩溃（与原地雷页相同）。

原页面已有的字段是同一个字段对象，继续保存到原来的配置条目。实现见 `offline/component_view.lua`（通用组件视图）、`offline/throwable_components.lua`、`offline/thrower_components.lua`。

## 地雷页

“实体组件 → 地雷”标题旁有两个按钮，分别打开两个组件：

- **地雷（MinefieldComponentData，44 字节，11 项）**：一颗地雷本身。13 个实体：敌方雷区（地雷区及 MK2–MK8）、MD-6 / MD-8 / MD-i4 / MD-17 和 G-11 铁蒺藜。参数组：触发（触发延迟、连锁引爆延迟、解除保险时间、接触即触发、可触发的最小单位体型、触发体）、爆炸与 AI 回避（爆炸 ID，AI 回避半径）、音效、未知字段（+0x28）。爆炸 ID 是引用：带类型标记，双击打开对应的爆炸记录，只接受本游戏版本存在的爆炸 ID。
- **地雷生成器（MineSpawnerComponentData，32 字节，7 项）**：敌方雷区如何布雷。8 个实体（地雷区及 MK2–MK8）。参数组：布雷范围（横向 / 纵向地雷数、雷区宽度 / 深度、位置随机偏移），未知字段（+0x00 所有记录同一个 64 位值，可能是资源哈希；+0x1C 开关）。RawData 没有这个组件的 dump，布局取自游戏类型库，数值由游戏数据核对。

原地雷战略配备页上的“Minefield / Mine”各行（投掷器编队 1、地雷生成器、地雷触发与爆炸）与这两页及投掷器页是同一个字段对象，两边同步。

## 挂载页

“实体组件 → 挂载”是 MountComponentData（120 字节，30 项，164 个实体）：一个实体上挂载的最多 5 个其他实体，如坦克炮塔、纵步者的武器、狂暴者的电锯。每个挂载位一个参数组（24 字节）：挂载的实体（u64 实体哈希，名称后显示实体名）、挂接节点、挂载侧（通用 / 右侧 / 左侧）、挂载名、+0x14 / +0x15 两个未知开关。

把挂载的实体换成不同类的实体，可能在生成时使游戏崩溃，提示中有说明。

## 背包页（物品栏）

“实体组件 → 背包”是 InventoryComponentData（144 字节，20 项，86 个实体）：

| 参数组 | 内容 |
| --- | --- |
| 默认装备 | 主武器、副武器、支援武器、投掷物、背包、近战武器（实体哈希，名称后显示实体名） |
| 治疗针 | 初始、补给、最大（所有实体目前都是 2 / 2 / 4） |
| 其他 | 可丢弃装备 |
| 未命名装备列表 | +0x40 起 10 个实体哈希；目前只有绝地潜兵本体的第 1 项有值（P-19 蟋蟀手枪） |

SEAF 页面“携带的武器”三行就是这里的主武器、副武器、支援武器：这三个字段在 SEAF 实体上沿用原页面的武器选择方式（从 SEAF 可用武器列表中选），两边同步。换成游戏没为该实体加载的装备会显示为缺失模型，把敌人的枪给 SEAF 曾使游戏崩溃，提示中有说明。

## 炮塔与制导页

“实体组件 → 炮塔与制导”标题旁有两个按钮：

- **视觉传感组件（SensorEyeComponentData，44 字节，11 项，315 个实体）**：视野范围（视距、余光距离、背后感知距离（-1 为无）、视野水平角、垂直角）、视线（视觉类型：无 / 人形 / 锥形 / 全向，视点节点，视线方向跟随视点节点，视线检测模板）、植被（此距离内无视植被、植被内可见距离）。敌人页的视距、视野角和炮台的侦测距离是同一组字段。
- **炮塔组件（TurretComponentData，76 字节，19 项，74 个实体）**：转动（水平 / 垂直转速、转速比例指数）、转动范围（水平 / 垂直最小最大角）、节点（垂直 / 水平转动节点、枢轴节点）、音效（转动 / 俯仰音效触发时间、各开始 / 停止音效、警告音效、两个未知事件）。炮台页的转速是同一组字段。

原页面先建立的字段若读取上限较小（如视距只读到 1000 米），在组件页沿用同一字段时把上限放宽，避免数值较大的实体（视距最大 3000 米）漏行。

## 地狱舱页

位于实体组件中护盾的右边，标题旁的按钮切换四个组件，每个实体一页，排版与生命页相同（组件 → 参数组 → 字段）。

| 按钮 | 组件 | 记录 | 字段 | 实体 |
| --- | --- | ---: | ---: | ---: |
| 地狱舱下落 | HellpodComponentData（0x7EF5CC55） | 104 字节 | 26 | 8 |
| 地狱舱载荷 | HellpodPayloadComponentData（0xDDB5C03F） | 12 字节 | 3 | 117 |
| 地狱舱挂架 | HellpodRackComponentData（0xA98BB156） | 568 字节 | 124 | 72 |
| 舰上地狱舱 | ShipHellpodComponentData（0x1E4344A9） | 4 字节 | 1 | 2 |

- **地狱舱下落**：变体、生成高度、初始速度、制动高度、制动速度、制动时间，以及 15 个音效事件。原“额外”页（已移除）中“地狱舱：初始空投 / 增援”的五个值就是这里的 +8、+20、+24、+28、+32；以前在那里保存的数值仍会生效。
  - 变体的取值已用游戏数据核对：初始空投（2）只出现在“绝地喷射舱 MK1”（生成高度 1500），增援（1）只出现在“绝地喷射舱 MK2”（1000 米、350 米/秒、350 米处制动），其余为载荷（0）。
  - 2024 年结构中没有的成员（+4、+0xC 两个浮点数、+0x24、+0x64）显示为“未知”。提示里写了各记录的取值：只有带预生成位置的那个地狱舱 +0xC 为 -400/400，+4 为 0，+0x64 为 1。
- **地狱舱载荷**：收回后移除时间、存续时间（-1 表示不限）、收回时能力。存续时间与哨戒炮/固定武器页的“部署持续时间（秒）”是同一字段。
- **地狱舱挂架**：8 个载荷槽，每槽包括物品（实体，标签后显示实体名）、挂点、位置/旋转偏移、部署/收回动画事件、收回音效、是否应用战备自定义差异、挂架侧（左/右）；另有最后收回延迟、禁用收回、地图图标与名称、三个音效事件、部署/最后收回能力、随机/生成载荷数量、禁用初始互动。
- **舰上地狱舱**：占用灯熄灭计时（游戏中两条记录都是 3 秒）。

字段布局全部来自游戏类型库，已用当前游戏的 `generated_entities.dl_bin` 核对：四个组件的全部 199 条记录都能按布局读出全部字段。字段名的来源如下：
- 载荷、挂架：来自 RawData dump，按全部实体的数值对齐；

## 护盾 / 投掷物 / 投掷器 / 地雷 / 阵营 / 挂载 / 物品栏 / 视觉 / 炮塔 / 武器的验证

三个组件的解析经过两路独立核对：

1. **游戏类型库**：解密当前游戏的 `dl_library.dl_typelib`，把三个记录逐层展开到最底层（含内联数组、嵌套向量、UnitEffect、引信项、编队、位域）。护盾 83 个、投掷物 78 个、投掷器 186 个叶子成员，与解析的字段一一对应，偏移、宽度和类型全部一致。
2. **游戏数据与 RawData**：解密 `generated_entities.dl_bin`，从实体表取出全部 15 / 46 / 5 条记录，按解析的偏移读出每个字段，与 [Darctor/Helldivers2_RawData](https://github.com/Darctor/Helldivers2_RawData)（1.007.200）的数值逐项比较：1245、3588、930 个值全部相同。

武器类 25 个组件共 1631 个叶子成员与类型库一一对应，13 个有 dump 的组件共 206410 个值与 RawData 比较，仅 WeaponData +0x194（crosshair_type）有 3 个实体不同（dump 之后的游戏更新或已改动的文件）；全部填充字节为 0。视觉传感组件 11 个叶子成员、315 条记录 3465 个值，炮塔组件 19 个叶子成员、74 条记录 1406 个值，与 RawData 全部相同，视觉传感的 3 个填充字节全为 0（炮塔无填充）。物品栏组件 20 个叶子成员、86 条记录 1720 个值与 RawData 全部相同，3 个填充字节全为 0。挂载组件 30 个叶子成员、164 条记录 4920 个值与 RawData 全部相同，10 个填充字节全为 0。阵营组件 32 个叶子成员、533 条记录 17056 个值与 RawData 全部相同，填充字节全为 0。地雷组件 11 个叶子成员、13 条记录 143 个值与 RawData 全部相同；地雷生成器 7 个叶子成员与类型库一致，8 条记录从游戏数据读出（RawData 无此组件）。

核对中修正了两处：RawData 把投掷物的一个开关记作 `unk_bool_0x0155`，类型库和游戏数据都确认它在 +0x154（+0x155 是填充字节，全部为 0）；UnitEffect 的 +44 不是一个 u32，而是 1 个字节里的 5 个位域，现按 5 个开关显示。

页面始终显示全部字段。启动时仍会用已安装游戏的类型库再核对一遍；游戏更新导致布局变化时，标题下显示“注意：游戏类型库与解析不一致……”并写入日志（以 `shield:` / `throwable:` / `thrower:` 开头），此时修改前应先核对。

## 拆毁页

原顶部单独的实体拆毁入口移入实体组件，成为“生命与拆毁”的“实体拆毁”标签。拆毁现在直接使用生命页的原生控件和页面框架，不再切换到独立前端。阈值覆盖、自动保存、恢复和安装流程保留，仍与原炮台页面共用统一的拆毁设置。切换子页或写入游戏前提交当前数值；无效输入会阻止提交。
